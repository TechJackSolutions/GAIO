## Purpose

This guide is for third parties -- reviewers, clients, auditors, and integrators -- who want to verify a GAIO Configuration Tag or a GAIO configuration file. It publishes the two artifacts Module 13 references but does not embed in model-consumed output: the Normalization Spec v1 and the tag JSON Schema. It also documents the verification procedure.

A core rule of the GAIO hash architecture: **hashes are a widget responsibility, not an AI responsibility.** The GAIO widget computes cryptographic hashes at configuration generation time and embeds them in the configuration file header. The AI's role is to read and reference these embedded hashes in the tag -- never to independently compute or fabricate them. This separation ensures hash integrity (the widget has exact bytes) and prevents fabrication (the AI never produces a hash it cannot verify).

The tag attests to configuration, not compliance. A valid tag proves that a GAIO configuration was loaded; it does not prove that every response in the session perfectly followed that configuration. See Limitations below.

## The Configuration Tag

The tag is a portable attestation block certifying which GAIO configuration was active when work was produced. It includes configuration metadata, a unique Tag ID, and references to verification hashes generated by the widget at configuration creation time.

### Tag ID format

```
GAIO-TAG-YYYYMMDD-XXXXXXXX
```

Example: `GAIO-TAG-20260218-4f7c2e1a`

- **Date portion:** `YYYYMMDD` from the tag generation timestamp.
- **Identifier portion:** 8 hexadecimal characters generated as a session-unique identifier at tag creation time.
- Machine-validation pattern (from the JSON Schema): `^GAIO-TAG-\d{8}-[0-9a-f]{8}$`
- The Tag ID is a reference label, not a cryptographic artifact. It identifies the attestation; the widget-embedded hashes verify the configuration. These are separate functions.

### Tag fields

Required fields (populated from the active configuration; unextractable fields are marked `[not detected]`, never guessed):

| Field | Purpose |
|-------|---------|
| GAIO Version | Framework version traceability |
| Tag ID | Unique attestation identifier; audit linkage |
| Enforcement Mode | Enforcement posture (Full Enforcement / Integrity Lock) |
| Primary Domain | Scoping context |
| Secondary Domain(s) | Extended scoping, or "None" |
| Sub-Domain(s) | Specialization detail |
| Authority Level | Engagement depth indicator |
| Configuration Weight | Config depth (Full / Standard / Compact) |
| URL Policy | Source restriction posture (Option A / B / C) |
| Configuration Date | When the config was generated |
| Tag Generation Timestamp | ISO 8601, generated at invocation |

Optional fields:

| Field | Inclusion Rule | Purpose |
|-------|---------------|---------|
| Purpose Statement | Include if present and non-empty; omit field entirely if blank | User-authored context for reviewers |
| Canonical Hash (SHA-256) | Include if present in config header; note absence if not | Exact file integrity verification (widget-generated) |
| Normalized Hash (SHA-256) | Include if present in config header; note absence if not | Content integrity verification across deployment methods (widget-generated) |
| Normalization Spec Version | Include whenever Normalized Hash is present | Tells verifiers which normalization rules were applied |

## The Two Hashes

The GAIO widget computes two SHA-256 hashes at configuration generation time:

**Canonical Hash (SHA-256):** Computed from the raw bytes of the configuration output string as generated. This hash verifies exact file integrity -- any byte-level change (including encoding corruption) produces a different hash.

**Normalized Hash (SHA-256):** Computed after applying the Normalization Spec to the configuration output string. The normalization removes encoding-sensitive characters (smart quotes, Unicode dashes, etc.) before hashing, producing a hash that survives copy-paste encoding variance. This hash verifies semantic content integrity across deployment methods.

Both hashes are embedded in the .txt file header at download time (and in copy-to-clipboard output) and displayed in the widget's metadata badges:

```
# Canonical Hash (SHA-256): [canonical_hash]
# Normalized Hash (SHA-256): [normalized_hash]
# Normalization Spec: v1
```

**Important (from the reference implementation):** the hashes are computed over the generated configuration text BEFORE these three header lines are inserted. The widget inserts the hash lines into the file only at copy/download time, immediately after the `# Weight:` header line. A verifier must therefore remove the three hash lines before recomputing either hash. See Verification Procedure.

## Normalization Spec v1

The Normalization Spec defines the transformations the widget applies before computing the Normalized Hash. The same spec is published here for external verifiers who want to independently verify the Normalized Hash against their copy of the configuration. It is not included in the model-consumed output because the AI does not perform normalization.

Apply the rules in order:

| Order | Character Class | Normalization Rule |
|-------|----------------|-------------------|
| 1 | Byte Order Mark (BOM) | Strip (U+FEFF, U+FFFE) |
| 2 | Line endings | Normalize all to LF (\n). Replace CRLF (\r\n) and lone CR (\r). |
| 3 | Unicode em-dash | Replace with ASCII double-hyphen (--) |
| 4 | Unicode en-dash | Replace with ASCII hyphen (-) |
| 5 | Smart double quotes | Replace with ASCII straight double quote (") |
| 6 | Smart single quotes | Replace with ASCII straight single quote (') |
| 7 | Unicode right arrow | Replace with text equivalent (-->) |
| 8 | Unicode left arrow | Replace with text equivalent (<--) |
| 9 | Unicode bidirectional arrow | Replace with text equivalent (<-->) |
| 10 | Unicode checkmark | Replace with [x] |
| 11 | Unicode bullet | Replace with ASCII hyphen (-) |
| 12 | Trailing whitespace | Strip from each line |
| 13 | Multiple consecutive blank lines | Collapse to single blank line |
| 14 | Leading file whitespace | Strip |
| 15 | Trailing file whitespace | Strip |

Reference-implementation precision (from `normalizeForHash()` in the widget; use these to reproduce byte-exact behavior):

- Rule 1 strips a single leading U+FEFF or U+FFFE only (regex anchored to file start).
- Rule 5 covers U+201C and U+201D; rule 6 covers U+2018 and U+2019.
- Rule 7 = U+2192, rule 8 = U+2190, rule 9 = U+2194.
- Rule 10 covers both U+2713 and U+2714; rule 11 = U+2022.
- Rule 12 strips spaces and tabs (`[ \t]+`) at end of each line.
- Rule 13 collapses runs of 3+ LFs to exactly two (one blank line).
- Rules 14/15 strip leading and trailing whitespace of the whole file.

**Versioning:** The spec is versioned (v1). Changes to these rules produce a new version. The widget embeds the normalization version in the file header alongside the hashes. Verifiers apply the version stated in the file, not the latest version. Existing hashes remain valid under their stated version.

**Future expansion:** Additional character classes may be added in v2+ as new corruption patterns are identified. New versions are additive -- they do not change rules for characters already covered.

**Mojibake note:** The normalization spec addresses source Unicode characters. It does not attempt to reverse double-encoded mojibake artifacts (e.g., multi-byte corruption sequences from UTF-8/Windows-1252 round-trips). A mojibake-corrupted config will produce a different Normalized Hash than the clean original. This is correct behavior -- it indicates encoding corruption occurred, and the verification pathway should flag encoding variance.

## Verification Procedure

Two pathways exist. A reviewer checking the Canonical Hash needs the original .txt file. A reviewer checking the Normalized Hash needs the Normalization Spec (above) and the ability to apply it to their copy.

### Common preparation

1. Obtain the configuration text (the downloaded .txt file or the copied configuration).
2. Read the expected hash values from the header lines `# Canonical Hash (SHA-256):`, `# Normalized Hash (SHA-256):`, and the spec version from `# Normalization Spec:`.
3. Remove those three header lines from the text. The widget computed the hashes before inserting them, so they are not part of the hashed content.
4. Hash inputs are the UTF-8 encoding of the text (the widget uses `TextEncoder`, which produces UTF-8). Hash output is lowercase hexadecimal.

### Pathway 1 -- Canonical Hash (exact file integrity)

1. Take the prepared text (hash lines removed) exactly as-is -- no other modification.
2. Compute SHA-256 over its UTF-8 bytes.
3. Compare against the embedded Canonical Hash.

### Pathway 2 -- Normalized Hash (content integrity across deployment methods)

1. Take the prepared text (hash lines removed).
2. Apply the Normalization Spec at the version stated in the file (v1 rules above), in order.
3. Compute SHA-256 over the UTF-8 bytes of the normalized text.
4. Compare against the embedded Normalized Hash.

### Interpreting results

- **Both hashes match:** the configuration is byte-identical to what the widget generated.
- **Canonical mismatch, Normalized match:** the file's bytes changed but only in ways the spec normalizes away (line endings, smart quotes, dashes, etc.). Semantic content integrity holds; encoding variance occurred in transit.
- **Both mismatch:** the configuration content was modified after generation (or was corrupted beyond encoding variance, e.g., mojibake). The file cannot be verified against the tag; treat it as a different configuration.
- **Hashes absent from the header:** the config was deployed without preserving the hash header lines (partial copy-paste, manual reconstruction, or hand-written without the widget). The tag is still valid as configuration metadata, but it cannot be cryptographically verified.

The tag system provides the data for verification; it does not perform the verification. Detecting whether a loaded config is a legitimate GAIO configuration is the role of this hash verification pathway -- the reviewer compares the tag's hashes against a known-good reference.

## Reference Implementation

The authoritative implementation lives in `widget/GAIO_Widget_v1_0.html`:

- `normalizeForHash(text)` -- Normalization Spec v1 as a 15-step string replacement chain (lines ~1496-1514).
- `computeGaioHashes(outputText)` -- computes both hashes: SHA-256 via `crypto.subtle.digest('SHA-256', ...)` over `TextEncoder` (UTF-8) bytes; canonical from the raw output string, normalized from `normalizeForHash(outputText)`; hex-encoded lowercase (lines ~1516-1524).
- `getHashHeaderLines()` -- produces the three header lines embedded in the file (lines ~1526-1529).
- `generateOutput()` -- builds the configuration and triggers async hash computation and badge display (hash badges with copy-full-hash actions, lines ~2099-2120).
- `copyOutput()` / `downloadOutput()` -- insert the hash header lines immediately after the `# Weight:` line at copy/download time (lines ~2131-2145).

## Limitations

- **The tag attests to configuration, not compliance.** A valid tag proves that a GAIO configuration was loaded. It does not prove that every response in the session perfectly followed that configuration. Compliance assessment is the role of Module 14 (Self-Audit Report).
- **Hash availability depends on deployment method.** If the config was deployed without preserving the hash header lines, hashes will not be available in the tag. The tag is still valid without hashes -- it provides full configuration metadata -- but it cannot be cryptographically verified.
- **The tag cannot detect fake configurations.** If someone loads a fabricated config with correct GAIO header formatting but invented content, the tag will attest to it. Verification against a known-good reference via the hash pathway is what detects this.
- **Hash verification requires the original file or the Normalization Spec.** The Canonical Hash pathway needs the original .txt file; the Normalized Hash pathway needs this spec applied to your copy.
- **Tag ID uniqueness is sufficient for document linkage, not database-scale deduplication.** The 8-character hex identifier is not designed as a primary key for high-volume centralized systems.

## Known Discrepancies (Section 13 prose vs. widget implementation)

1. **Header block example vs. actual generated header.** Section 13's "Updated Header Block" example shows `# Primary Domain:`, `# Secondary Domain(s):`, and `# Authority Level:` as header comment lines, with the hash lines after them. The widget's actual generated header contains only: `# GAIO Configuration`, `# Generated:`, `# Standard:`, `# Created by`, `# Mode:`, `# Weight:` -- domain and authority values appear in the Module 02 body (as `**Primary Domain:**` etc.), not as `#` header lines -- and the hash lines are inserted immediately after `# Weight:`. Verifiers should key on the three hash lines themselves, not on the documented header layout.
2. **Hash-line exclusion is implicit in Section 13.** Section 13 states a reviewer "needs the original .txt file" but does not state that the three embedded hash header lines must be removed before recomputing. The widget computes both hashes before inserting those lines, so removal is required (documented in Verification Procedure above).
3. **BOM rule scope.** Spec rule 1 says "Strip (U+FEFF, U+FFFE)" without a position qualifier; the widget strips only a single leading occurrence at the start of the file.
